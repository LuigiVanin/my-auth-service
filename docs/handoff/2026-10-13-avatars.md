# Handoff para o frontend: avatares de usuário, organização e aplicação

Destino: `auth-service-frontend`, checado em `./frontend`, no commit `568a3cc`.
Origem: `auth-service`, feature `docs/features/2026-10-11-avatars/`.

**Um campo novo em toda resposta e nove rotas novas. Tudo é aditivo:** nenhum campo
existente mudou de nome ou de tipo, então nada quebra se o frontend subir antes ou
depois do backend.

---

## ⚠️ Não vai funcionar de cara — e isso é esperado

O backend está pronto, mas **as chaves de integração com a AWS ainda não existem**.
O bucket está criado; a distribuição do CloudFront e o usuário IAM do backend ainda
estão sendo configurados (`docs/features/2026-10-11-avatars/aws-console-setup.md`,
passos 3 a 5). Sem eles, o `.env` do backend não tem `STORAGE_PUBLIC_BASE_URL` nem
as credenciais, e o serviço sobe **sem storage**.

Enquanto for assim, o comportamento da API é este, e é o comportamento correto:

| O quê | Hoje, sem as chaves | Depois das chaves |
| --- | --- | --- |
| `avatar_url` em qualquer resposta | sempre `null` | a URL da CDN, ou `null` sem avatar |
| `POST …/avatar/upload` | `501 NOT_IMPLEMENTED` | `201` com o formulário assinado |
| `PUT …/avatar` | `501 NOT_IMPLEMENTED` | `200` com o sujeito atualizado |
| `DELETE …/avatar` | `501 NOT_IMPLEMENTED` | `200` com `avatar_url: null` |

O que dá para fazer **agora**:

- os tipos, a exibição com `src={x.avatar_url ?? undefined}` (cai nas iniciais, que
  é o que já aparece hoje);
- o componente de troca de imagem inteiro: seleção, recorte, redução para webp;
- os três services e as mutations;
- o tratamento do `501`: o botão de trocar imagem fica desabilitado com uma dica
  ("upload de imagens indisponível neste ambiente"), em vez de um erro genérico.
  É o único ramo testável ponta a ponta hoje, e é o que o ambiente sem storage vai
  responder para sempre.

O que **só dá para testar depois**: o envio real ao S3 (passo 2 abaixo), a
confirmação e a imagem servida pela CDN. Quando as chaves entrarem, siga o roteiro
da seção 7.

---

## 1. `avatar_url` em toda resposta

Todo `User`, `Organization` e `App` que a API devolve passa a carregar:

```ts
/** URL pública pronta para `<img src>`, ou null sem avatar. Sempre presente. */
avatar_url: string | null;
```

Vale para login, register, refresh, authorize, listagens, detalhes, os `PUT` de
edição, `reset_password`, `verify_email` e `change_email` — **e para as cópias
aninhadas**: `current_organization` do usuário, `owner_user` e `organization` da
aplicação, `users_pool.owner_user` e `users_pool.organization`,
`participants[].user`.

Nos tipos, três linhas:

| Arquivo | Interface |
| --- | --- |
| `src/types/users.ts` | `CoreUser` (e, por herança, `AuthUser`) |
| `src/types/organizations.ts` | `Organization` |
| `src/types/apps.ts` | `App` |

O nome segue o resto do contrato, em `snake_case`. **Atenção ao catálogo:** o
exemplo do `Avatar` em `steering/component-catalog.md` usa `user.avatarUrl`, que
não existe — o campo é `avatar_url`.

**A URL muda a cada troca.** Cada envio gera uma chave nova, e a imagem é servida
com cache de um ano. Não acrescente `?t=` nem nada para "furar" cache: uma URL nova
já é uma imagem nova.

## 2. Onde a imagem aparece

| Onde | Arquivo | Hoje |
| --- | --- | --- |
| Menu do topo | `components/console/layout/UserMenu.tsx` | `<Avatar name={user.name} />` |
| Configurações da conta | `components/console/settings/AccountSettingsPanel.tsx` | `<Avatar name={current.name} size="lg" />` |
| Configurações da organização | `components/console/settings/OrganizationSettingsPanel.tsx` | `<Avatar name={organization.name} size="lg" shape="rounded" />` |
| Seletor de organização | `components/console/organizations/OrganizationSwitcher.tsx` | quatro `<Avatar>` com o nome |
| Aplicações | `components/console/apps/AppClientCard.tsx`, `AppClientRow.tsx`, `pages/console/AppDetailPage.tsx` | sem avatar hoje |

Os três pontos de **troca** de imagem cabem onde a edição já mora:
`AccountSettingsPanel` (usuário), `OrganizationSettingsPanel` /
`OrganizationEditFields` (organização) e `AppDetailPage` (aplicação).

Duas coisas no `Avatar` (`components/ui/Avatar.tsx`) merecem atenção antes:

- **Ele não tem fallback para erro de carregamento.** Com `src`, renderiza
  `<img>` direto; uma URL que responda erro mostra imagem quebrada, não as
  iniciais. Vale um `onError` que volte para as iniciais — principalmente agora,
  com a CDN ainda sendo montada.
- O `alt=""` é intencional (o nome está ao lado), mantenha.

## 3. As rotas

| Sujeito | Autorizar | Confirmar | Remover |
| --- | --- | --- | --- |
| Usuário autenticado | `POST /core/users/me/avatar/upload` | `PUT /core/users/me/avatar` | `DELETE /core/users/me/avatar` |
| Organização atual | `POST /core/organizations/{id}/avatar/upload` | `PUT /core/organizations/{id}/avatar` | `DELETE /core/organizations/{id}/avatar` |
| Aplicação da organização atual | `POST /core/apps/{id}/avatar/upload` | `PUT /core/apps/{id}/avatar` | `DELETE /core/apps/{id}/avatar` |

**Permissão:** as três rotas de cada sujeito pedem a mesma permissão da edição
dele — `as::users::me::UPDATE`, `as::organizations::UPDATE`, `as::apps::UPDATE`.
O botão de trocar imagem aparece exatamente onde o de editar já aparece; use o
mesmo `can(...)` de `useCan()` que a tela já usa para a edição — por exemplo
`can("as::apps::UPDATE")` em `AppDetailPage.tsx`.

## 4. O fluxo: três passos

O arquivo **nunca passa pelo backend**. O backend assina, o navegador envia direto
ao S3, o backend confirma.

```ts
// src/services/avatars.ts — esboço
import { api } from "@/lib/api";

export interface UploadGrant {
  key: string;
  url: string;
  fields: Record<string, string>;
  expires_at: string;
  max_bytes: number;
}

export type AvatarContentType = "image/png" | "image/jpeg" | "image/webp";

// subject: "users/me" | `organizations/${id}` | `apps/${id}`
export async function requestAvatarUpload(subject: string, contentType: AvatarContentType) {
  const { data } = await api.post<UploadGrant>(`/core/${subject}/avatar/upload`, {
    content_type: contentType,
  });
  return data;
}

/** Fora do `api`: ver abaixo. */
export async function sendToStorage(grant: UploadGrant, file: Blob): Promise<void> {
  const form = new FormData();
  for (const [name, value] of Object.entries(grant.fields)) form.append(name, value);
  form.append("file", file); // por último, sempre

  const response = await fetch(grant.url, { method: "POST", body: form });
  if (response.status !== 204) throw new StorageUploadError(response.status);
}

export async function confirmAvatar<T>(subject: string, key: string) {
  const { data } = await api.put<T>(`/core/${subject}/avatar`, { key });
  return data;
}

export async function removeAvatar<T>(subject: string) {
  const { data } = await api.delete<T>(`/core/${subject}/avatar`);
  return data;
}
```

Detalhes que mudam o comportamento:

- **O passo 2 não pode passar pela instância `api`.** Ela injeta `Authorization:
  Bearer …` e os headers do `AppGuard` em toda chamada, e tem `baseURL`. O S3 tenta
  autenticar qualquer `Authorization` que receba e recusa a requisição. Use `fetch`
  puro (ou uma instância de axios limpa), sem header nenhum — o `FormData` define o
  `Content-Type` sozinho.
- **O arquivo vai por último no `FormData`.** O S3 ignora qualquer campo depois
  dele. A ordem dos demais não importa.
- **O tipo do blob tem que ser o pedido no passo 1.** O formulário assinado fixa o
  `Content-Type`; outro é recusado pelo S3.
- **2 MiB no máximo**, travado no próprio S3. Tipos aceitos: `image/png`,
  `image/jpeg`, `image/webp` — SVG não, de propósito. A recomendação é recortar em
  quadrado e reduzir para 512 px em webp no navegador antes do passo 1, o que deixa
  o arquivo abaixo de 200 KB; o limite é só a rede de baixo.
- **A autorização vale 5 minutos** (`expires_at`). Peça no momento do envio, não
  ao abrir o modal.
- **Confirmar devolve o sujeito inteiro**, no mesmo formato do `PUT` de edição
  dele, com o `avatar_url` novo.
- **Remover é idempotente**: sem avatar, responde `200` com o mesmo corpo.

## 5. Depois de confirmar ou remover: o cache

- **Usuário:** invalide `userKeys.me()`, como o `AccountSettingsPanel` já faz
  depois do `updateMe`. Mas o `UserMenu` lê o usuário de `useAuth()`, que vem da
  **sessão salva no login**, não da query — sem mais nada, o menu do topo só mostra
  a imagem nova no próximo refresh ou login. Para atualizar na hora, regrave o
  usuário da sessão com a resposta da confirmação (`saveSession` em `lib/api.ts`).
  A edição de nome hoje tem a mesma limitação.
- **Organização:** invalide a lista de organizações (o `OrganizationSwitcher` lê
  dela) e o detalhe, se houver.
- **Aplicação:** invalide a lista e o detalhe da aplicação.

## 6. Erros

| Status | Rota | Significa | O que fazer |
| --- | --- | --- | --- |
| `501` | qualquer | o backend está sem storage — **é o estado atual** | desabilitar a troca de imagem com a dica da seção inicial |
| `400` | autorizar | `content_type` fora da lista | bug do cliente |
| `400` | confirmar | a `key` não é de uma autorização deste mesmo sujeito | bug do cliente: a key do passo 1 tem que ir sem alteração |
| `404` | confirmar | nada foi enviado com essa `key`: expirou, o envio falhou, ou já foi confirmada | recomeçar do passo 1 |
| `422` | confirmar | o arquivo no S3 não é o que foi assinado (tamanho ou tipo) | recomeçar; não deveria acontecer |
| `403` | organização | `{id}` não é a organização atual (mesma regra do `PUT` de edição) | — |
| `404` | aplicação | a aplicação não é da organização atual | — |

**Os erros do passo 2 vêm do S3, não da API:** corpo em XML, sem o `code` de
problem detail, então o `describeApiError` não serve. Os que aparecem na prática:
`400` (arquivo acima de 2 MiB), `403` (autorização expirada, ou tipo diferente do
assinado). Trate qualquer status diferente de `204` como "o envio falhou" e
ofereça tentar de novo — que é recomeçar do passo 1.

## 7. Quando as chaves entrarem

O backend avisa quando o `.env` tiver as credenciais. Aí, nesta ordem:

1. `POST /core/users/me/avatar/upload` responde `201`, não `501`. Se ainda for
   `501`, o backend não carregou o storage — o log de boot dele diz quais
   variáveis faltam.
2. O envio do passo 2 responde `204`. Um erro de **CORS** no console do navegador
   aqui é configuração do bucket, não do frontend: o bucket aceita `POST` de
   qualquer origem nesta fase, mas vale reportar.
3. A confirmação responde `200` com `avatar_url` preenchida, e a URL abre no
   navegador. Uma URL que responda `403` logo depois de criada é a CDN ainda sem
   permissão no bucket — reportar ao backend.
4. Trocar a imagem gera uma URL **diferente**; remover volta `avatar_url` para
   `null`, e o `Avatar` volta às iniciais.
